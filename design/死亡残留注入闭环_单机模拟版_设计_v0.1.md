# 死亡→残留注入闭环 · 单机模拟版 · 设计方案 v0.1

> 状态:**已实现**(2026-09-16,见决策日志 D-115)。承接检索到的 roadmap 缺口清单;
> 对应 canon `逃离AI_开发规格_v3.1.md` §3.6(玩家残留 M12/M13/M14)+ §3.8(M24 漂流瓶)。

---

## 0. 范围声明:为什么是"单机模拟版",不是原版

canon §3.6/§3.8 设计的是**真·多人异步**——"残留"来自其他真实玩家的死亡记录,需要
服务端存所有人的死亡数据、全局令牌桶(M13)、墓场随机抽取池(M14)、认领/回流账本
(M24)。**这个项目目前是纯前端单机(localStorage 存档,没有后端,玩家之间零数据
交换)**。做真多人版是另立一个基础设施项目,规模远超这份文档能覆盖的范围,拍板已
定这次不做。

这次做的是**同一条思路的单机模拟**——D-109 拍板③已经在 `BOTTLE_POOL` 上验证过
这条路子:用几个写死的 canon NPC(黑话名 `#6404-C`、`#5502-D` 等)假扮"历任真实
采样员",全部是预先手写的固定内容,不是真实玩家数据。这份方案把同一手法铺到
M12(遗留会话节点)/M13(残响对峙)/M14(墓场遗物回收)。

## 1. 现状盘点:已经覆盖了多少

| canon 机制 | 现状 |
|---|---|
| M24 漂流瓶(一对一,可带资源) | **已做**——`BOTTLE_POOL`(框架共享池,4 张 NPC 瓶)+ `OWN_BOTTLE`(你自己上一封信,取自 `SV.history` 末条) |
| M14"捡自己的旧机"例外(新手路径) | **已做**——`SCREENS.oldPhone`/`residueRead`,`PREV_INST` 取自 `SV.history`,B 局 `lastEnding==='captured'` 时可回收/只带走遗言 |
| M14 捡到**同伴(NPC)**遗物 → 回收/归还二选一 | **没做**——现在只能捡自己的,捡不到别人的 |
| M12 遗留会话节点(聊天片段+理由+遗言+死者最后预测,热度分级) | **没做**——`BOTTLE_POOL` 的瓶是"一对一私信",不是"挂在某个 node 上、随时可能撞见"的残留 |
| M13 残响(对峙、稀有度分档、非语言通道优先) | **完全没做** |

**结论**:M24 这条私信线已经很扎实,这次要补的是**M12(挂点残留)+ M13(残响
对峙)+ M14 的"捡到别人遗物"那一半**——三者共用同一批"历任 NPC 采样员"素材,
是一件事的三个呈现面,不是三套独立系统。

## 2. 单机模拟设计

### 2.1 素材层:扩展"历任采样员"名册(框架共享,不分底本)

现有 canon NPC 黑话名只有 `#6404-C`(preDeath 教学范例)+ 4 张漂流瓶的作者
(`#5502-D`/`#3120-K`/`#1177-B`/`#8891-R`)。这次把他们提升成一份**统一的 NPC
名册**,每人补全 M12 需要的字段:

```js
const LEGACY_ROSTER = {
  '#5502-D': { causeTag: '窗口内违规', lastWords: '...', reason: '...',
               heat: 'stale', node: 'th_stranger' },
  ...
};
```

- `heat`:canon 是真实时间戳分档(屏幕还亮/手还温/隔夜/陈迹);单机版没有"其他
  玩家刚刚死"这种事,**改用固定/半随机标签模拟**——每个 NPC 在名册里配一个固定
  `heat` 档位(如 `#5502-D` 常年"陈迹",呼应他已经死了很久的设定),不追求真实
  时间感,只追求"读起来有梯度"。
- `node`:这条残留挂在**哪个交互点**上(呼应 canon"挂 node"),即在现有框架
  的哪个屏幕/深搜层里可能撞见——复用已有屏幕(`th_stranger`/`tools`/`deleted`
  等),不新开一整套"残留地图"UI。
- 新增 NPC 数量:建议 2–3 个(与漂流瓶池独立编号),避免和瓶的"来信"语气重复——
  瓶是"写给你的信",M12 残留节点是"你顺手翻到的痕迹",语域不同。

### 2.2 M12:遗留会话节点

- 触发:在**已有的**深搜/交互流程里(比如某次"深搜·成功"之后),小概率(参考
  BOTTLE_POOL 的稀有度)附带一句"这里有别人的痕迹"提示,进一个新的只读小屏
  `SCREENS.legacyNode`,展示:`[死因标签] · [热度档] \n [聊天片段/理由/遗言]`。
- **死者最后预测**(canon 原句式`系统 91% 确定他会在这一格断连。他没有。`)——
  这条本身就是"秘匿数值"的反讽用法(明说一个数字,再告诉你它错了),照搬这个
  句式,数字来自 NPC 名册里固定写死的值,不联动真实概率表(避免和 P2 幻觉门禁
  §4 的秘匿隔离红线冲突——这条数字是叙事装饰,不是真实机制数值,要在文案里
  明确"这是系统的错误预测"语境,不能被误读成真实活规则参数)。
- 每 node 展示上限、淘汰权重(canon"新鲜度×认领数")在单机版简化成:**每局最多
  撞见 1 条**,不做认领计数(没有其他玩家来认领)。

### 2.3 M13:残响对峙

- 触发:比 M12 更稀有,作为一次性的"节拍屏"插入(参考 `SCREENS.dilemma`/
  `SCREENS.huntArrive` 的既有节拍位模式,不新增导航结构)。
- **怪异度四档**照搬 canon 原文分类,每档配 1–2 句手写文案(L0 手写,不走 LLM——
  这是"死者的复读故障",越像故障越对,不需要生成式多样性):
  1. 语气正常,唯一异常是时间感错误
  2. 复读生前片段 + 答非所问
  3. 只用"死者写过的词"重组句子(挑 NPC 名册里已经写过的词,拼句子,制造"听得懂
     但拼不成人话"的效果)
  4. 放弃对话,循环播报同一句
- **言语稀缺预算**(≤3/局)+ **非语言通道优先**(已读未读/"正在输入"不发送/
  点赞旧照)这条纪律直接复用——非语言通道比对话便宜实现得多,建议**优先做非
  语言这半**(比如在某个已有屏幕的状态栏偶尔飘过"对方正在输入…"然后消失),
  对话版本(四档文案)作为第二阶段。**第二阶段已实现,见决策日志 D-115 第二阶段。**
- **对峙胜负**(缓存子集 40–60%):单机版没有"从墓场设备里双重扣除"的必要
  (没有真实墓场池),简化成常规 `ENGINE.act` 数值结算,机制上等价"一次特殊的
  高风险遭遇",复用 `verdict`/受限裁决(D-105)的既有 pickBranch 模式。

### 2.4 M14:捡到 NPC 遗物(补上"回收/归还"二选一)

- 扩展现有 `deleted`/`oldPhone` 逻辑:当**没有**自己的旧机残留可捡(`oldPhoneAvail()`
  为假)时,小概率改为出现"NPC 名册"里某个人的遗物(从 `LEGACY_ROSTER` 里抽,
  排除本局漂流瓶已经给过的那位,呼应"排除同指纹集群"的精神,不用真做指纹系统)。
- 两个选项:
  - **① 回收**:获得资源(同现有 oldPhone 的 `回收` 分支数值结构)。
  - **② 归还**:呼应 canon"经漂流瓶寄回原主的下一个实例,给你信标值"——单机版
    没有"原主的下一个实例"可寄,**替代实现**:归还 = 追加进 `BOTTLE_POOL`
    共享池一条"你把它还回去了"的新瓶(下一局、甚至下一台机子的玩家会读到"有人
    归还过一件东西"),用已有的漂流瓶追加机制(D-110 拍板③"底本可追加"）兑现
    "信标值"——不新增经济系统,复用瓶池当账本。

## 3. 与现有三台底本的关系:框架共享,不分底本

`LEGACY_ROSTER`(历任采样员名册)和 `BOTTLE_POOL` 同一性质——这些 NPC 是"整个
采样计划"的老资历,不属于任何一具具体案子,三台机子(phone-7741/5029/3319)应该
共用同一份名册,不需要像 `narrative.*` 那样按底本各写一份。这也是这次设计**不
需要动 DOSSIER schema**的原因,新增内容直接挂在 `content.js` 顶层,和 `BOTTLE_POOL`
放在一起。

## 4. 复用点(不重新发明轮子)

- 遭遇/对峙的"引擎算结果集,LLM/脚本只挑分支"红线 → 复用 D-105 `pickBranch`/
  `resolveBranch`/`verdict`。
- 稀有触发概率结构 → 复用 D-101 陷阱条款"`GRADER_TIER>=1 && Math.random()<0.7`"
  同款写法。
- 秘匿隔离扫描面 → M12"死者最后预测"里的数字必须过 D-111 `hallucination_gate.js`
  的 SECRET 词表检查(这条文案容易不小心带出真实窗口/概率值,写的时候要小心)。
- 归还经济复用瓶池追加机制,不新增账本结构。
