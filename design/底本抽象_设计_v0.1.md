# 底本抽象 · 设计 v0.1

> 目标:把"一台失联设备的可玩内容"从框架里剥出来,成为一份**数据**(底本),让
> `content.js` 从"写死一个副本"变成"读底本渲染"的引擎。这是"深耕国内副本 / 副本
> 工厂产线化(§6.1)"的地基。
> 状态:**待审**(先出方案再动手)。审定后转成落地任务,写进 [决策日志](决策日志.md)。

---

## 0. 为什么是"底本形",和《苏丹的游戏》的区别(先钉这个)

**《苏丹的游戏》不是副本结构**:它是「一个世界 + 一个巨大的事件/卡牌/角色库 + 一个
周循环」,把内容按情境拉进**一条连续的人生**。没有"副本选择",是"我自己的这一世"。

**逃离AI 的核心幻想是"每次接入一台不同的、别人的、已经结束的失联设备"**——每局一个
新死者、新故事、新机子。这天然是**副本/底本形**,塞不进"一条连续人生"的模子。而且它正好
接上免费档经济:每台机子可**独立预生成**(§6.2,免费档前提),再靠**人生×圣像×管辖区**
三维参数化组合出量(#9 覆盖度)。

**我们比苏丹多一层**:苏丹只有"一条连续人生"这一层连续性;逃离AI 是
**per-局底本(那台机子)+ 一层跨局 meta(世界日报 / 恐怖游轮化残留 / 采样官加码)**。
那层 meta = 我们的"连续世界"感,**已经实现**,保持在框架侧,读底本产物。

**命名**:数据单元叫「**底本**」(一台设备的剧本),避开"副本"在 MMO 刷本语境的包袱。

**结论(本方案不动的前提)**:结构上是底本形(每局一台机子);实现上要做的是
"**一台机子的内容 = 数据,框架 = 引擎**"。

## 1. 边界:什么是框架(共享),什么是底本(per-机子)

抽象的成败在这条线划得准不准。逐类清点当前 `content.js`/`engine.js` 里的东西:

### 框架(共享引擎 · 不进底本)
- **呈现层**:`lcd.js` 全套(渲染/腐蚀/震屏/变暗)、外壳 `index.html`、呈现 helper
  (`statusBar`/`softKeys`/`option`/`optSlim`/`btn2`/`scrollView`/`settleLines`)。
- **判定与数值机制**:`engine.js` 的 `RULE`/`CHECK`/`roll`/`act`/`downgradeFail`/
  `inWindow`/`violate`——**机制**是共享的;具体**数值/窗口**是底本参数(见 §2)。
- **骨架调度**:`schedule`/`pendingInterrupt`/`afterAction`/`S.beats`——单局流程的
  **节拍骨架**共享;哪个节拍放什么内容由底本填。
- **受限裁决**:`verdict`/`pickBranch`/`resolveBranch`/`pickBranchLLM`——共享。
- **LLM 代理管道**:`rou.js` 的 persona 分派 / 三级降级 / 输出 lint / HMAC 签名 /
  限流 / 供应商可插拔——**管道**共享;**人格核文本**是底本(见 §2.6,关键)。
- **福祉/合规**:危机 break-glass、当日静默、AI 声明、柔柔一键关断、失焦冻结——共享。
- **存档框架**:`save.js`(schema 版本号、跨局字段);具体字段值随底本。
- **跨局 meta**:世界日报框架、恐怖游轮化(disposalHistory/momLocked 机制)、采样官
  加码(GRADER_TIER)——**机制共享**;它们**引用**的底本产物(死者名义/线程)随底本。
- **门禁体系**:`tools/*`——共享;其中**内容类门禁(证据链/布局/时长)对每个底本都要跑**。

### 底本(per-机子内容 · 一份数据)
- 死者身份 + 关系人 cast(阿帆/柔柔/妈/老周/舅…)。
- 格子/线程清单(收件箱/菜单里有哪些 app、线程,各自文案与成本)。
- 证据 E1–E5 定义 + 证据链(哪次深搜解锁哪条证据、它们拼出的真相)。
- 线索/真相文本(阿帆委托柔柔、病逝 47 天…)。
- 活规则窗口参数、掉落/成本表偏移。
- 漂流瓶内容、遭遇叙述、两难、陌生人真/饵、结局文案、处置回声。
- 采样官指令库的**措辞**(机制共享,文案随底本)。
- **四个 LLM 人格核 + 注入白名单**(柔柔/妈/陌生人/采样官——见 §2.6)。

> 划线原则:**"换一台机子会变的" = 底本;"换一台机子不变的" = 框架。**

## 2. 底本 schema 草案(字段定义)

一份底本 = 一个对象(可 JSON 化,便于预生成/缓存/校验)。**现在能手写,将来工厂能填**。

### 2.1 meta(身份与参数化坐标)
```
meta: {
  id: 'phone-7741',              // 底本 id
  deceased: { name:'沈一帆', alias:'阿帆', died:'47 天前', cause:'病逝' },
  life:    'programmer',          // 人生(§6 三维之一;决定 cast/线程题材)
  icon:    'the-companion',       // 圣像(§7 12 圣像之一;决定基调/美术皮)
  jurisdiction: 'all-nighter',    // 管辖区(§5.4 四类;决定活规则/难度偏移)
  scenarios: ['A','B'],           // 支持的场景(教学局 / 二次接入)
}
```
> 人生×圣像×管辖区 = 内容格点三维。手写时随便填;工厂化时由格点组合驱动(#9 覆盖度追踪)。

### 2.2 cast(关系人)
```
cast: {
  companion: { key:'rou', label:'柔柔 ♥', ... },   // 对应 LLM 人格 companion
  mother:    { key:'mom', label:'妈', ... },
  contacts:  [ { key:'zhou', label:'老周', ... }, ... ],
}
```

### 2.3 threads(格子/线程)——收件箱与菜单里的可交互内容
每条:label / 未读徽标规则 / 页文(可深翻) / 每步成本 / 关联证据 id。
> 现在 `inboxItems()` 里那一串就是这个的写死版。

### 2.4 evidence(证据链 E1–E5)——**幻觉门禁的锚**
```
evidence: {
  E1: { name:'秒回避实', source:'th_mom deep', truthFrag:'...' },
  ...
  chain: [ 'E1','E2','E3','E4','E5' ],   // 集齐 = 真相 truthDone
  truth: '阿帆委托柔柔以他名义回复所有来信…',
}
```
> **P2 幻觉门禁**就断言:LLM 辅助撰写出的底本里,`chain` 每条都有唯一 `source`、
> 集齐后 `truth` 成立、任何一次生成都不丢/不移位证据(§4)。

### 2.5 rules / drops(活规则窗口与数值偏移)
```
rules: { windowGen:{...}, dropTable:{...}, checkOverrides:{...} }
```
> 机制在 `engine.js`;这里只放**这台机子的参数**(窗口起点、掉落值、成功率偏移)。

### 2.6 personas(LLM 人格核 + 注入白名单)——**最关键、也最敏感**
换一台机子,柔柔/妈就是**别的人**(不同死者的伴侣/母亲)。所以人格核**是底本内容**,
框架只提供管道。
```
personas: {
  companion: { core:[...], stateLines:'...', lint:{...} },
  mother:    { core:[...], safe:[...], ... },
  stranger:  { core:[...], real:'...', bait:'...' },
  grader:    { core:[...], taunts:[...], verdicts:{...} },
}
```
> **硬约束(不因底本化而松)**:①`persona_sync` 仍要求 core 在"客户端底本 ↔ 服务端"
> 逐字一致(底本走服务端时,core 从底本注入 `rou.js`,签名/校验不变);②秘匿隔离
> 仍在框架侧强制(窗口值/概率永不进 persona 文本);③危机护栏是**框架级**,不随底本改。

### 2.7 encounters / dilemmas / bottles / endings
遭遇叙述、两难池、漂流瓶、结局文案、处置回声——都是文本+分支数据,机制留框架。

## 3. 落地策略:抽取即回归(先一字不变)

**不新增任何玩法。** 把现有这一个副本抽成 `holbein-7741` 底本,游戏行为**逐字不变**,
靠现有 179 条门禁 + `duration_audit` + 全屏布局扫描守住零漂移。

小步、每步提交、每步全绿:
1. **最容易剥的先**:证据/线索/文案表 → 从 content.js 常量搬进底本对象,content.js 改
   为读底本。跑全套门禁证明零漂移。
2. threads/inbox → 底本驱动。
3. rules/drops 参数 → 底本。
4. personas(core)→ 底本注入(persona_sync 改成"从底本取 core 比对",仍逐字)。
5. encounters/dilemmas/bottles/endings → 底本。
6. 收口:`content.js` 里不再有硬编码内容,只有引擎 + 一句 `loadDobon(CURRENT)`。

> 每一步都是"结构搬家",不是"改玩法"。门禁是这次大重构的安全网——半年前没这套护栏
> 不敢动 content.js,现在敢。

## 4. 与 P2 幻觉门禁的接口(并肩做)

底本一旦变数据 + 上 LLM 辅助撰写,**证据链幻觉是头号风险**(白日梦验证"解谜幻觉率必为零")。
门禁形态:对一份底本,断言
- `evidence.chain` 每条有唯一可达 `source`(深搜路径存在);
- 集齐 chain ⇒ `truthDone` 成立;缺任一条 ⇒ 不成立;
- LLM 辅助撰写产出的底本,跑 N 次,**每次**证据链都不丢/不移位/不新增幻觉证据;
- persona 文本不泄秘匿(复用现有 persona_sync 秘匿扫描,按底本跑)。
> 抽取即回归阶段先用**现有手写底本**建立这套门禁(有牙齿:改坏 chain 即报警),
> 到 P4 LLM 撰写时它就是产线的质量闸。

## 5. 风险 / 未决(审的时候一起定)

1. **参数化生成 vs 纯手写**:schema 要不要现在就为"人生×圣像×管辖区自动填充"留槽,
   还是先只支持手写、生成留到 P4?(倾向:**留槽但不实现**——字段按可生成的形状设计,
   眼下手写。)
2. **persona core 底本化后的 persona_sync**:改成"从底本取 core 比对"是否引入新的
   秘匿泄漏面?(需要单独一条门禁守:底本→服务端注入路径不夹带秘匿。)
3. **漂流瓶的归属**:瓶是"历任采样员"留的,半跨底本——放框架共享池,还是每底本一份?
   (倾向:框架共享池 + 底本可追加,呼应 §3.8 真实玩家残留的将来接入。)
4. **抽取粒度**:一次性抽完 vs 分 6 步小步(倾向小步,门禁守每步)。
5. **B 局(剧本 B)**:B 是"同一台机子二次接入",应是同一底本的 scenario 分支,不是
   另一个底本——schema 里 `scenarios:['A','B']` 表达。确认这个理解。
