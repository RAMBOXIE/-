## D-111 P2 幻觉零容忍门禁进CI

**背景**:承接 D-109 §4"与 P2 幻觉门禁的接口"——底本一旦变数据、未来交给 LLM
辅助撰写,证据链幻觉是头号风险。D-110 做出第二份底本后,证据链结构(`evidence.
{name,source}` + `chain` + `truth`)第一次有两个独立样本可比对,是把这条门禁从
"设计意图"落成"能跑的断言"的合适时机。

**落地**:新增 `tools/hallucination_gate.js`(纯 Node 脚本,复用既有 `mkEnv` 引擎
拉起手法),自动被 `tools/run_all.js` 的目录扫描纳入——"进CI"在这个项目里就是
"放进 tools/ 目录",不需要额外接线。断言四类:
1. **chain 完整性**:`chain` 无重复、每个 id 在 `evidence` 里有非空 `name`+`source`。
2. **可达性**:从 `content.js` 源码里提取真实触发点(`evidence('Ex')` 调用 +
   `S.evidence.Ex = true` 直写两种写法都扫),与底本 `chain` 做双向比对——框架会点亮
   但底本没声明 = 幽灵触发点;底本声称有但框架点不亮 = 幽灵证据。两份底本目前都是
   `{E1,E2,E3,E4,E5}`,完全对上。
3. **chain 长度 = 5**:`SCREENS.e5crack`/案卷显示等十余处framework 代码硬编码了这个
   数——**门禁选择把"5"当框架结构性约定去守,而不是反过来把十几处显示代码改成读
   `chain.length`**(过度泛化;两份底本都恰好是 5,YAGNI)。
4. **秘匿隔离**:复用 `persona_sync.js` 的 `SECRET` 词表,但**收窄扫描面到
   `evidence`(证据名/来源/真相文案)**——不扫 `narrative` 全量:陷阱条款文本本就该
   把违规规则明说给玩家("先给限制后给破绽"是陷阱条款的设计初衷,不是泄密面),录音
   /聊天时间戳("[32天前 03:14]")是普通叙事时间不是活规则窗口值,两者都在早期版本
   里被错误地一并扫描,产生了 3 个误报(命中 DOSSIER_A 的 `T_WINDOW` 陷阱文案与
   DOSSIER_B 的录音时间戳),排查后确认是门禁扫描面过宽,收窄后误报消失,断言收紧到
   §4 原文写的"底本的证据名/来源/真相文案"这一句所指的确切范围。

**验证方法论**(沿用本项目"先用未修复代码验证会报警"的老规矩):门禁脚本自带一组
"教学假底本"——故意在 `chain`/`evidence`/`truth` 里各埋一种坏形状(重复 id、缺
name、缺 source、长度不对、真相只给一页、秘匿词泄漏、幽灵证据、幽灵触发点),先断言
检查函数对着假底本真的会报警,再对两份真底本各跑一遍确认全绿。这样"检查函数本身有
没有牙齿"和"两份底本是否干净"是两组独立断言,不会因为真底本凑巧没触发过某个检查
分支而误以为门禁生效。

**范围说明**:§4 提到的"LLM 辅助撰写产出的底本跑 N 次、每次证据链都不丢/不移位"
这一条,本轮**不做**——现在两份底本都是手写的,没有 LLM 撰写产线可供"跑 N 次"抽样,
留到 P4 真上 LLM 撰写底本时再补(那时候这条门禁的意义才成立)。

**验证**:`npm test`(除已知 B 局时长缺口)全绿,`hallucination_gate.js` 的 11 条
断言(7 条教学验证 + 2 份底本各 1 条综合断言 + 1 条前置抽取断言)全部通过。

## D-121 LCD 像素字体稍微缩小

**背景**:用户反馈"游戏文字稍微缩小一点"。追问确认范围:只改字体本身尺寸
(不是整个设备画面的 CSS 等比缩放)——这条改动比表面看起来重,LCD 是像素
点阵模拟渲染(`js/lcd.js`),字号由 `CELL_H`(字高)/`CW_ASC`(半角字宽)/
`LINE_H`(行距)三个像素常量控制,而全项目的按钮/文字布局(`content.js` 里
上百处 `y += LH + 2` 式的间距计算、`optSlim`/`option` 的行高、
`layout_scan_checks.js` 的重叠检测)全部动态引用这几个常量,理论上牵一发
动全身。

**实现**:`js/lcd.js`——`CELL_H: 14→13`,`CW_ASC: 7→6`,`LINE_H: 16→15`;
CJK 满格字宽此前硬编码字面量 `14`(和 `CELL_H` 脱节的独立写死值),改成
跟读 `CELL_H`,避免两处尺寸各改各的、字形变形。三个常量同比例微降
(≈7%),字略小一档,不到"改一半"的量级。

**为什么没伤到布局**:项目里所有换行(`L.wrap`)、行距(`content.js` 读
`LCD.LINE_H` 而非硬编码 16)、字宽度量(`L.textWidth`)都走 `lcd.js` 导出的
函数动态计算,没有任何调用方直接手算像素宽度——字号一变,这些函数自己
重新算,换行点、行高跟着字号走,不需要逐屏手调。唯一的连带效应是:同样
的屏幕宽度现在能多塞几个字,原本卡在行尾的词换行点会挪动(见下方验证
里 `attribution_checks.js` 暴露的问题)。

**发现并修复一处因此产生的测试脆性**:`tools/attribution_checks.js` 的
"回收单 · 仅作答后打印归因行"用例把整帧渲染出的每一行文字用 `｜` 拼接后
做子串匹配,断言 `'对本实例参数不成立'` 整段连续出现。字号缩小后这句归因行
的换行点恰好落在这段文字中间,被拆成两次 `drawText` 调用、中间夹了一个
`｜` 分隔符,子串匹配失效——**游戏本身渲染完全正确**,只是测试用例对"这句
话不会跨行"这个从未被断言过、也不该被断言的细节做了隐性假设。修法:
断言前把 `｜` 分隔符去掉再比对(`t.replace(/｜/g, '')`),这样不管字号/
屏宽如何变化、换行点落在哪,断言只关心"这几个字最终连续出现在画面上"这
个真正要测的东西——这是让测试更健壮,不是为了迁就这次改动而放水。

**验证**:`node tools/layout_scan_checks.js` 连续 3 次重跑,63 屏布局扫描
全绿,0 处按钮/文字重叠(改小字号没有让任何一屏的按钮和正文挤到一起)。
`node tools/run_all.js`——除 `attribution_checks.js`(已修复,见上)外无
新增失败;`tools/bottle_checks.js` 单独跑绿,`run_all.js` 里出现过一次

那种一次性教学死亡)跑三种策略、每种跑 N 局统计死亡率:
- **裸退**:进`tools`直接选"2 直接断连(弃缓存)"——理论上应该是随时可用的
  保底解,不经过任何真实判定。
- **均衡**:正常探索(读瓶/翻已删除目录,吃 25% 伏击判定)但不闯违规窗口,
  最后尝试上传(吃 `resolveUploadB()` 的 `roll('final')`/`roll('save')`)。
- **贪婪**:额外在违规窗口内回两次消息(第二次触发真实 `roll('c90')`+
  `b90fail()` 判定链)、多翻几次相册深搜推高溯源,再尝试上传。
遗留节点(legacyNode)/预测卡(predict)这两个纯 cosmetic 的随机插屏
(20%/若干%概率打断任意一次导航)会被通用 `drainCosmetic()` 自动关闭——
和 [[D-122]]/[[D-124b]] 撞过的是同一类坑,这次直接在驱动层面统一处理掉,
不会被误判成"卡死"。

**结果(N=3000/策略,真随机)**:
| 策略 | 死亡率 | 主要死因 |
|---|---|---|
| 裸退 | **0.0%** | — |
| 均衡 | 24.1% | 上传期被定位·自救失败(561)/挂标记目录伏击(162) |
| 贪婪 | 41.7% | 二次违规·采样窗收网(645)/上传期被定位(420)/挂标记目录伏击(185) |

永远有效解存在,不存在"必死"的退化状态。**
② **贪婪确实比均衡更危险,而且差距是真实代码里的判定链算出来的,不是
摆设的难度数字**——贪婪比均衡多担了"二次违规"这一整条独立风险(645 次死因,
均衡策略完全不会撞上,因为它从不闯窗口),死亡率从 24.1% 涨到 41.7%,涨幅
主要就来自这条本可以完全避开的风险。

不闯窗口),"贪婪"策略也没有把每一条能撞的风险都撞满(比如没有故意多触发
几次伏击、没有刻意拖到极限缓存)。两边不是同一个模型,数字对不上是意料之中;
真正要的结论(裸退保底解成立/风险分层在真实代码里确实存在且方向正确)已经
拿到,不需要为了逐字对齐纸面模型的具体档位再去调这份脚本的策略强度。

**验证**:分别用 N=15/30(调试用,抓出并修掉 `legacyNode` 随机打断导致的
