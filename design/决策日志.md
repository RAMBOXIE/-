## D-111 P2 幻觉零容忍门禁进CI

**背景**:承接 D-109 §4"与 P2 幻觉门禁的接口"——底本一旦变数据、未来交给 LLM
辅助撰写,证据链幻觉是头号风险。D-110 做出第二份底本后,证据链结构(`evidence.
{name,source}` + `chain` + `truth`)第一次有两个独立样本可比对,是把这条门禁从
"设计意图"落成"能跑的断言"的合适时机。

**落地**:新增 `tools/hallucination_gate.js`(纯 Node 脚本,复用既有 `mkEnv` 引擎
拉起手法),自动被 `tools/run_all.js` 的目录扫描纳入——"进CI"在这个项目里就是
"放进 tools/ 目录",不需要额外接线。断言四类:
1. **chain 完整性**:`chain` 无重复、每个 id 在 `evidence` 里有非空 `name`+`source`。
2. **可达性**:从 `content.js` 源码里提取真实触发点(`evidence('Ex')` 调用 +
   `S.evidence.Ex = true` 直写两种写法都扫),与底本 `chain` 做双向比对——框架会点亮
   但底本没声明 = 幽灵触发点;底本声称有但框架点不亮 = 幽灵证据。两份底本目前都是
   `{E1,E2,E3,E4,E5}`,完全对上。
3. **chain 长度 = 5**:`SCREENS.e5crack`/案卷显示等十余处framework 代码硬编码了这个
   数——**门禁选择把"5"当框架结构性约定去守,而不是反过来把十几处显示代码改成读
   `chain.length`**(过度泛化;两份底本都恰好是 5,YAGNI)。
4. **秘匿隔离**:复用 `persona_sync.js` 的 `SECRET` 词表,但**收窄扫描面到
   `evidence`(证据名/来源/真相文案)**——不扫 `narrative` 全量:陷阱条款文本本就该
   把违规规则明说给玩家("先给限制后给破绽"是陷阱条款的设计初衷,不是泄密面),录音
   /聊天时间戳("[32天前 03:14]")是普通叙事时间不是活规则窗口值,两者都在早期版本
   里被错误地一并扫描,产生了 3 个误报(命中 DOSSIER_A 的 `T_WINDOW` 陷阱文案与
   DOSSIER_B 的录音时间戳),排查后确认是门禁扫描面过宽,收窄后误报消失,断言收紧到
   §4 原文写的"底本的证据名/来源/真相文案"这一句所指的确切范围。

**验证方法论**(沿用本项目"先用未修复代码验证会报警"的老规矩):门禁脚本自带一组
"教学假底本"——故意在 `chain`/`evidence`/`truth` 里各埋一种坏形状(重复 id、缺
name、缺 source、长度不对、真相只给一页、秘匿词泄漏、幽灵证据、幽灵触发点),先断言
检查函数对着假底本真的会报警,再对两份真底本各跑一遍确认全绿。这样"检查函数本身有
没有牙齿"和"两份底本是否干净"是两组独立断言,不会因为真底本凑巧没触发过某个检查
分支而误以为门禁生效。

**范围说明**:§4 提到的"LLM 辅助撰写产出的底本跑 N 次、每次证据链都不丢/不移位"
这一条,本轮**不做**——现在两份底本都是手写的,没有 LLM 撰写产线可供"跑 N 次"抽样,
留到 P4 真上 LLM 撰写底本时再补(那时候这条门禁的意义才成立)。

**验证**:`npm test`(除已知 B 局时长缺口)全绿,`hallucination_gate.js` 的 11 条
断言(7 条教学验证 + 2 份底本各 1 条综合断言 + 1 条前置抽取断言)全部通过。
