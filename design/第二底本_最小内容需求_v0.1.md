## 2. 必须新写的两块——独立 LLM 人格核(machine #2 专属,不可复用)

复核了 `js/companion.js`/`mom.js`/`stranger.js`/`grader.js` 四个人格文件:

- **`companion.js`(柔柔核)**:系统提示词**直接写死** "你是「柔柔」…登记用户:沈一帆(阿帆)…
  你爱的是阿帆,只爱阿帆" ——是完整的人物关系/口吻/秘密设定,不是可参数化的模板。
  machine #2 的伴侣人格要真的"不一样",这份提示词、离线兜底正则表(`re: /阿帆|沈一帆|.../`)、
  以及状态触发行(`st.e4`/`st.truth`/`st.disposal` 对应的台词)**全部要重写**,并且要过
  `tools/persona_sync.js`(客户端 core ↔ `netlify/functions/rou.js` 逐字校验)。
- **`mom.js`(妈核)**:同样写死了"你的儿子沈一帆(帆)已经不在了",且这是**全项目最高
  敏感度**的一面(丧子母亲台词 + crisis break-glass 护栏)。新写不是填空,是完整的人物
  写作 + 安全测试(自伤语过滤/不哀求/语域限制),工作量和风险都在这里最大。

**这两块是 machine #2 真正的成本大头**——不是代码量大,是**人物写作 + 安全审校**的
工作量大,且每一处改动都要过 `tools/persona_sync.js` 与既有的安全门禁(护栏正则/回退
脚本)。

## 3. 可以完全不碰的部分(框架级共享,machine #2 不用管)

## 4. 唯一的真实结构缺口:目前 `DOSSIER` 是单例,不是"选一份"

D-109 的 `CURRENT = DOSSIER` 是硬绑定,`loadDossier(id)` 目前只是"校验后原样返回"——
**没有"选哪一份底本"这件事的地基**。接第二台机子时,下面这些consts 要从"唯一一份"
变成"按当前底本选择哪一份"(纯文本表,无闭包,结构性工作量小,但目前确实没做):

`CONTACT_ROWS` / `inboxItems()` 引用的标签 / `MOM_PAGES` / `MOM_TOLD_PAGES` /
`ALBUM_SEQ` / `ROU_PAGES` / `RECS` / `STRANGER_LIB` / `PREDS_A` / `PREDS_B`

以及:

- **存档需要 `dossierId` + `dossierCycle` 两个字段**:前者记住这一局挂在哪台机子上
  (避免读档时读错底本),后者是隐藏的切换计数器(§7-1 拍板:`disposal` 收线后下一局 +1)。
  `js/save.js` 目前都没有。
- **不需要"选底本"UI 屏**——§7-1 已拍板为全自动隐藏切换,玩家从不主动选。

## 5. 建议的最小可行范围(MVP)

**不建议**现在就做"任意 N 台底本"的通用注册表(数组/工厂/随机抽选整套机制)——
两台底本时,`if (dossierId==='phone-7741') ... else ...` 级别的硬分支完全够用,
过早通用化是在猜第三台机子的形状。建议顺序:

1. 从 §6 三个候选里选定人生题材(推荐②信息流成瘾者×AD-007)。
2. 写 `DOSSIER_B` 内容(§1 清单)+ `MOM_PAGES_B`/`ROU_PAGES_B`/`TRAP_LIB_B`/
   `DILEMMA_POOL_B` 等新文本表(§7-2/3 已拍板:直接写字面量,不做 DSL/注册表)。
3. 新写柔柔核-B/妈核-B 两份人格提示词(§2,含 persona_sync 校验 + 安全测试)。
4. `SAVE` 加 `dossierId`/`dossierCycle` 两个字段;`loadDossier(id)` 从"只有一个"
   改成"按 id 挑一个"(两个 if 分支即可,不做注册表)。
5. 实现 §7-1 拍板的自动切换点:`disposal` 收线 → 下一局 `dossierCycle+1` → 静默换底本,
   不加任何"选底本"UI。
6. 照 D-109 的老规矩:每步跑满门禁(`npm test` + `layout_scan` + `duration_audit`),
   两台机子各自独立回归,互不漂移。

本轮**明确排除**:多底本自动生成、英文/出海切片、她系统全量代际引擎——这些是
之前讨论过的更大 roadmap 项,与"能不能接出第二台机子"这件事无关,不在这份文档范围。

## 6. IP Bible 核对:machine #2 的人生题材不是白纸,canon 已经点了名

查了 `research/逃离AI_开发规格_v3.1.md` §6.3(内容路线)+ 归档策划案(v0.2/v0.4/M0冻结)。
canon 的"内容格点"公式是 **机主人生(∞) × 圣像机制(12 类,`AD-001`–`AD-012`) × 管辖区动词(4)**,
且**立项纪律要求"无来源圣像不入库"**(§1.10)——不是随便编一个新人设,而是从 12 类圣像
机制里挑,登记来源。

canon 内容路线表(§6.3)**已经明确点了 S1 阶段的三个候选**(machine #1 = 原型 =
`失踪者 × AD-006(克隆爱人)+AD-002(凝视/已读回执)`,已实现):

| 候选 | 人生题材 | 圣像机制 | 机制原意(据归档策划案) |
|---|---|---|---|
| ① | **云盘囤积者** | AD-001(数据圣母/采集场) | 囤积型题材,机制原意偏"教学区/基础循环",归档里叙事细节最薄——选它等于还要自己从零把机制原意想清楚 |
| ② | **信息流成瘾者** | AD-007(供给者/推荐女神) | "刷 feed 找线索,每次下滑耗电,feed 在读你,停不下来的代价";宪法 14①"供给者货真价实,唯一代价=接受即被建模" ——**机制原意最完整**,且与现有"电量/信号/缓存"三仪表天然契合(feed=另一种消耗节奏) |
| ③ | **审核员** | AD-010(过滤天使/系统安全中心) | "搜得到带不出:查扣博弈纵深";与管辖区"强审查型·夹带"玩法(D-109 rules.windowGen 已有的活规则骨架)高度同构,**天然带一套新数值张力**(查扣概率),但也意味着要为它设计新机制而非纯换皮 |

**推荐①→不选,②优先**:AD-007(信息流成瘾者)机制原意最完整、canon 原文给出的
"代价=接受即被建模"这条恐怖钩子和"她"系统的建模恐惧同构,叙事上直接可以和 machine #1
（"AI 伴侣代死者说话"）拉开差异又不跳出题材grid;AD-010(审核员)次优,但它的"查扣博弈"
是新机制,超出"结构搬家"范围,量级更接近一次新玩法开发,不算"最小内容需求"。
AD-001 因为归档里机制原意最单薄,不建议选(选了还要先把"数据圣母"这个圣像机制本身
从零定义,不是内容问题是设计问题)。

## 7. 拍板记录(2026-09-16)

1. **机子怎么切换(拍板)**:自动切换,**编号完全隐藏**——玩家永远不会看到"第二台机子"
   这类字样,只通过内容感知(新的死者姓名/新的证据链/新的柔柔核措辞)。触发点建议挂在
   `S.disposal` 上——玩家对 machine #1 做出处置选择(继续/删除/告知,`SCREENS.disposal`
   §2.7)那一刻,视为"这具案子收线了";**下一次开局**(存档里 `dossierCycle` 计数 +1)
   静默切到下一份 `DOSSIER`。落地上不需要注册表,两台机子时就是
   `dossierCycle % 2 === 0 ? DOSSIER_A : DOSSIER_B`。
2. **陷阱库要案子专属(拍板,推翻 §3 早先"复用通用库"的默认建议)**:`TRAP_LIB` 改为
   按当前底本取——不需要 mini-DSL,`detect()` 闭包本来就只引用泛化引擎状态
   (`S.violations`/`S.residueClaimed` 这类,不含具体案情文本),**直接写两份字面量数组**
   `TRAP_LIB_A`/`TRAP_LIB_B`,按 `dossierId` 选其一即可,和 §5 MVP 的"两个 if 分支"
   原则一致,不升级成注册表/DSL。
3. **两难抉择池的 UX 评估(供参考)**:有实质意义,不是可有可无的调味——它是"骨架固定位
   插一条良心/风险取舍"(D-106 原意),是整个游戏"资源管理"表皮下唯一一处**真正的价值观
   选择**,和最初讨论苏丹的复仇时对比的"持续人生"结构里道德抉择的作用是同一件事,建议
   **保留且案子专属化**。复核代码发现它被 D-109 步⑤误判了成本——`POOL` 里的文本本来就
   引用了 machine #1 的具体人物("阿帆"/"妈"),machine #2 必须换一份,但**换法不需要
   mini-DSL**:两难池目前就是"文本 + 两个引擎闭包"的字面量数组,直接写 `DILEMMA_POOL_B`
   (结构照抄现有 `POOL`)、按 `dossierId` 选择即可——mini-DSL 只有在想把两难做成
   "数据驱动可批量生成"时才用得上,不是接第二台机子的必要条件,不再算作本轮的架构缺口。
4. **人设**:见 §6,待选定 ①/②/③ 之一(推荐②)。
5. **工期**:先定稿(不进入实现),等 ①②③候选拍板后再排期开工。
