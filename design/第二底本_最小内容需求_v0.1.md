## 2. 必须新写的两块——独立 LLM 人格核(machine #2 专属,不可复用)

复核了 `js/companion.js`/`mom.js`/`stranger.js`/`grader.js` 四个人格文件:

- **`companion.js`(柔柔核)**:系统提示词**直接写死** "你是「柔柔」…登记用户:沈一帆(阿帆)…
  你爱的是阿帆,只爱阿帆" ——是完整的人物关系/口吻/秘密设定,不是可参数化的模板。
  machine #2 的伴侣人格要真的"不一样",这份提示词、离线兜底正则表(`re: /阿帆|沈一帆|.../`)、
  以及状态触发行(`st.e4`/`st.truth`/`st.disposal` 对应的台词)**全部要重写**,并且要过
  `tools/persona_sync.js`(客户端 core ↔ `netlify/functions/rou.js` 逐字校验)。
- **`mom.js`(妈核)**:同样写死了"你的儿子沈一帆(帆)已经不在了",且这是**全项目最高
  敏感度**的一面(丧子母亲台词 + crisis break-glass 护栏)。新写不是填空,是完整的人物
  写作 + 安全测试(自伤语过滤/不哀求/语域限制),工作量和风险都在这里最大。

**这两块是 machine #2 真正的成本大头**——不是代码量大,是**人物写作 + 安全审校**的
工作量大,且每一处改动都要过 `tools/persona_sync.js` 与既有的安全门禁(护栏正则/回退
脚本)。

## 3. 可以完全不碰的部分(框架级共享,machine #2 不用管)

- **`stranger.js`(陌生号码核)**:复核后发现这份 CORE **本来就是通用的**——"发错号码的
  陌生人,不知道对面是谁,不叫名字",没有任何案子特定信息。machine #2 只需要在
  `content.js` 里配一套新的 `STRANGER_LIB`(纯文本,零架构),LLM 人格核完全不用碰。
- **`grader.js`(采样官核)**:这是"母体"层面的全局实体,不属于任何一台机子,machine #2
  直接共用,不涉及。
- **`DIRECTIVE_LIB`/`TRAP_LIB`(采样官指令/陷阱库)**:通用采样官机制,`met()`/`detect()`
  引用的是泛化状态(`S.evidence`/`S.cacheVal`/`ENGINE.sigBars()`),不含具体案情——machine #2
  可以直接复用同一套指令池,不必现在为它专门写条目(要不要写案子专属指令是 §6 Q4)。
- **`engine.js` 的 `CHECK`/`dropTable`**:canon 蒙特卡洛校准值,继续框架共享,不随底本变。
- **两难抉择池(`SCREENS.dilemma`)**:D-109 步⑤已确认它嵌了可执行闭包,要案子专属内容需要
  先做动作-效果 mini-DSL——这件事本身独立于"接不接第二台机子",machine #2 若不需要专属
  两难剧情可以先绕开(见 §6 Q1/Q4)。

## 4. 唯一的真实结构缺口:目前 `DOSSIER` 是单例,不是"选一份"

D-109 的 `CURRENT = DOSSIER` 是硬绑定,`loadDossier(id)` 目前只是"校验后原样返回"——
**没有"选哪一份底本"这件事的地基**。接第二台机子时,下面这些consts 要从"唯一一份"
变成"按当前底本选择哪一份"(纯文本表,无闭包,结构性工作量小,但目前确实没做):

`CONTACT_ROWS` / `inboxItems()` 引用的标签 / `MOM_PAGES` / `MOM_TOLD_PAGES` /
`ALBUM_SEQ` / `ROU_PAGES` / `RECS` / `STRANGER_LIB` / `PREDS_A` / `PREDS_B`

以及:

- **存档需要一个 `dossierId` 字段**,记住这一局挂在哪台机子上,避免读档时读错底本
  (`js/save.js` 目前没有这个字段)。
- **需要一个"选底本"的触发点**——现在完全没有"下一局换一台机子"这件事,这是产品决定
  (见 §6 Q2),决定了要不要一个新的"选底本"UI 屏。

## 5. 建议的最小可行范围(MVP)

**不建议**现在就做"任意 N 台底本"的通用注册表(数组/工厂/随机抽选整套机制)——
两台底本时,`if (dossierId==='phone-7741') ... else ...` 级别的硬分支完全够用,
过早通用化是在猜第三台机子的形状。建议顺序:

1. 先拍板 §6 的开放问题(尤其 Q1/Q2),定下 machine #2 的人物设定与进入方式。
2. 写 `DOSSIER_B` 内容(§1 清单,纯内容工作)+ 新的 `MOM_PAGES_B`/`ROU_PAGES_B` 等文本表。
3. 新写柔柔核-B/妈核-B 两份人格提示词(§2,含 persona_sync 校验 + 安全测试)。
4. `SAVE` 加 `dossierId` 字段;`loadDossier(id)` 从"只有一个"改成"按 id 挑一个"
   (两个 if 分支即可,不做注册表)。
5. 决定并实现"怎么进入 machine #2"这一个入口(§6 Q2 的答案决定具体做法)。
6. 照 D-109 的老规矩:每步跑满门禁(`npm test` + `layout_scan` + `duration_audit`),
   两台机子各自独立回归,互不漂移。

本轮**明确排除**:多底本自动生成、英文/出海切片、她系统全量代际引擎——这些是
之前讨论过的更大 roadmap 项,与"能不能接出第二台机子"这件事无关,不在这份文档范围。

## 6. 开放问题(需要拍板)

1. **machine #2 的核心人设是什么?** 是继续"AI 伴侣代答已故用户"这个母题(只换死者/
   伴侣/母亲的具体人物),还是换一种"死者与生者关系"的结构(比如没有恋人只有兄弟姐妹、
   或换成父亲角色)?这决定 `cast` 的角色形状要不要跟着变,以及需不需要一份新的
   "父亲核"而不是复用"妈核"模板。
2. **玩家怎么进入 machine #2?** 现在每局都是 `#7741`。加入第二台后,是"下一次转生
   自动换新机子(旧机子退场)"、"按 `runCount` 或某种周期轮换"、还是"玩家在开局前选"?
   这决定 `SAVE.dossierId` 怎么维护,以及要不要一个新的"选底本"UI 屏。
3. **陷阱/指令库要不要案子专属条目?** 还是继续用通用 `DIRECTIVE_LIB`/`TRAP_LIB`(§3)。
4. **两难抉择池要不要 machine #2 专属剧情?** 如果要,意味着现在就要连带做动作-效果
   mini-DSL(D-109 步⑤已识别为独立架构工作);如果不要,machine #2 可以先绕开两难池
   自定义,沿用现有(不区分底本的)两难文本。
5. **工期预算?** 这决定是现在就动手,还是先把人设/文案定稿,统一开工。
