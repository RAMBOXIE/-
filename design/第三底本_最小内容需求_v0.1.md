## 1. 关键发现:AD-010 的机制原意,游戏里已经有一份现成实现

复核 `js/content.js` 发现 **"过滤层查扣"这套机制从 D-108 就已经存在**(`tools`/`upload`
屏:溯源 ≥70 时提示"过滤层查扣风险 25%",触发后缓存按比例损毁,`bottle_checks.js`/
`duration_audit.js` 都测过这条路径),只是它目前是**纯框架机制**,不属于任何一台机子的
"人生故事"——玩家看到的只是抽象的"平台审查",没有一张脸。

这正好是 machine #3 的差异化角度:**machine #3 的死者本人就是操作这套系统的人**——
他生前的工作就是"过滤天使"本体(内容审核员),现在这套系统反过来查扣**他自己**的遗物。
不需要新机制,只需要把 machine #3 的证据链/线索文案往"他的工作与他的死绑在一起"这个
方向写,让玩家在 `tools` 屏看到"过滤层查扣风险 25%"这条早已存在的提示时,多一层"这是
他曾经对别人做过的事"的反打——**纯内容工作,零新机制**,比 machine #2 的评估更干净
(machine #2 当初还要临时决定"要不要连带查扣新数值面",现在确认不需要)。

## 3. 架构:两个 if 分支到此不够用了——按 machine#2 文档当初的预留触发点,泛化成有序数组

`第二底本_最小内容需求_v0.1.md` §5 当时写过:"两台底本时,`if/else` 分支完全够用,
过早通用化是在猜第三台机子的形状"——现在真的要接第三台了,是时候把这个预留兑现:

**改动范围小,不是大重构**:
- `const DOSSIER = (SV && SV.dossierId==='B') ? DOSSIER_B : DOSSIER_A;` 
  → `const DOSSIER_ORDER = ['A','B','C'];`
    `const DOSSIER = { A:DOSSIER_A, B:DOSSIER_B, C:DOSSIER_C }[(SV&&SV.dossierId)] || DOSSIER_A;`
- `maybeSwitchDossier` 的 `nextId = raw.dossierId==='B'?'A':'B'` 
  → `nextId = DOSSIER_ORDER[(DOSSIER_ORDER.indexOf(raw.dossierId||'A')+1) % DOSSIER_ORDER.length]`
  (自动隐藏切换,拍板①原样沿用,只是从"翻转"变成"按顺序轮转")。
- 仍然**不做**独立注册表文件/插件式加载——三台机子的内容还是硬写在 `content.js` 顶部
  三个 `DOSSIER_X` 常量里,只是"选哪个"这一步从二选一变成查表,改动量是几行,不是架构。
